Storage Systems
Readmission risk prediction uses a Data Lake as the system of record for model features (historical EHR encounters, diagnoses, meds, labs, procedures) and a curated feature store (implemented as Delta/Iceberg/Hudi tables on the lake). The lake accepts raw/batch CDC from the EHR, preserves history, and supports schema evolution. Feature pipelines materialize training/serving features and publish risk scores back to a transactional app for clinicians.
Doctor plain‑English queries use a Vector Database paired with an NLP/LLM service. Unstructured clinical text (progress notes, discharge summaries, radiology impressions) is chunked and embedded; embeddings live in the vector DB for ANN (k‑NN) retrieval, while the original text remains in the document store/data lake for citations. Metadata filters (patient ID, date ranges, department) ensure context‑appropriate retrieval and auditability.
Monthly management reports run on a Data Warehouse (star schemas for admissions, bed occupancy, LOS, department costs). The warehouse is loaded from lake “silver/gold” tables to ensure governed, reconciled numbers with late‑arriving data handling and SCDs. BI tools read from the warehouse for consistent KPIs.
Real‑time ICU vitals land in a Streaming platform (Kafka/Event Hubs) and a time‑series store for high‑frequency writes and down‑sampling. Raw streams are also persisted in the lake for replay and retrospective analysis. Aggregated vitals feed bedside dashboards and can trigger alerting models.

OLTP vs OLAP Boundary
The OLTP boundary is the EHR and clinical operations systems where point‑of‑care transactions occur (orders, meds administration, charting). These systems prioritize ACID properties, low latency, and availability for clinicians. Data exits OLTP via change data capture (CDC) and scheduled exports.
The analytical boundary begins at the ingestion layer into the Data Lake. From here, batch/stream pipelines cleanse, de‑identify where required, and conform data into curated lake tables and the warehouse. Advanced analytics (feature engineering, model training, cohort building) as well as NLP embedding pipelines operate entirely on the analytical side. Risk scores and summarized insights that need to appear in the EHR are written back across the boundary through a controlled interface (e.g., a clinical decision support service), never allowing analysts to query OLTP directly. Operational dashboards that require sub‑minute vitals use the stream/time‑series path; enterprise KPIs use the warehouse.

Trade-offs
A key trade‑off is duplication and governance across multiple stores (lake, warehouse, vector, time‑series). This introduces operational complexity (more systems to run), consistency risks (which system is the source of truth for a given metric), and additional security surfaces for PHI. To mitigate:

Clear data contracts & lineage: define authoritative sources for each domain (e.g., lake bronze as raw, warehouse gold as KPI truth). Track lineage from OLTP → lake → warehouse/vector with a catalog and data quality rules (valid ranges for vitals, code set conformance, duplicate detection).
Write‑back discipline: risk scores and flags return to OLTP only through a versioned service that logs provenance, model version, and confidence, preventing “shadow writes.”
Unified governance: apply centrally managed access controls, encryption, and audit logs across all stores; isolate embeddings by patient and enforce row‑/column‑level policies so semantic search cannot cross patients. Regular privacy reviews ensure de‑identification where appropriate (e.g., model training on de‑identified corpora).
Operational SLAs: assign distinct SLOs—time‑series for sub‑minute freshness, vector search for sub‑second retrieval at patient scope, warehouse for daily‑close accuracy—so each system is optimized for its job without over‑engineering a single platform to do everything.

This architecture balances safety‑critical OLTP care delivery with flexible, scalable analytics and AI—meeting all four goals without compromising clinical integrity.
